# ACTIONS — the command surface (generated reference)

Every user-visible mutation goes through an `SAction` (see
`smaragd/main/actions/CONTRACT.md`). This maps each registered verb to its
class, source location, and XML attributes, for writing `.qxa` scripts and
headless tests. Keep it truthful when adding or changing an action.

Conventions (see also `smaragd/main/testkit/CONTRACT.md`):
- positions/durations are FRAMES at the project rate; fraction strings like
  `"48000/1"` parse via `parseFractionOrDouble`.
- clip/track paths are comma-separated child indices from the root mixer,
  e.g. `clip="0,1"` = track 0, child 1.
- a rejected `apply()` FAILS a headless test unless the action element has
  `expectReject="true"`.
- `nestedRejects="N"` (plan 53 B6, QBX-164) says the action's own INTERNALS are
  expected to submit N actions that legitimately refuse, and that the action
  itself must still apply. The runner decides whether an action failed by
  sampling `SActionHistory::rejectedCount()` around its submit, which cannot
  tell the action's own outcome from that of anything it submitted while
  applying — so a verb with a deliberate internal refusal reads as broken.
  `record-stop` is the first: it commits a pass, and a lane whose planner
  refuses it (plan 53 G11) would otherwise make `record-stop` look failed. The
  count is EXACT, so the action genuinely failing makes it N+1 and still fails
  the case, which `expectReject` would not catch. Attributing a refusal to the
  action that caused it needs the history to say WHICH action it refused, and
  that is a change in `actions/` with its own ticket.

## Addressing a SYSTEM LANE (proposal 45)

A SYSTEM LANE is a track the PROJECT owns rather than the user. It is
deliberately NOT among its root's `childLinks()`, so **no index path reaches
one** and `assert-track-count` cannot see it. Four spellings, and every verb
that takes a `trackPath` accepts the first two:

| Spelling | Reaches |
|---|---|
| `$master` | the root's master lane |
| `$master,0` | its CONDUCTOR lane — one system step, then a plain child index |
| `$send0`, `$send1`, … | send lane k, by creation (and file) order. **This is the CANONICAL spelling**, and what `pathToString()` writes |
| `$send:<name>` | the same lane by NAME — an INPUT spelling only |
| `Drums:$master` | any of the above in a named ARRANGEMENT |

Three things about it that are not guessable:

- **`$send:<name>` is resolved only by the verbs that parse their path at apply
  time**: the five plugin verbs (`insert-plugin`, `remove-plugin`,
  `reorder-plugin`, `set-plugin-bypass`, `set-plugin-param`) and
  `assert-system-lane`. A name maps to a sentinel only against a particular
  root, and `stringToPath()` is pure — it is called from `readXml()`, where
  there is no project — so it FAILS CLOSED there and
  `splacements::laneBySpec()` does the rewrite. Every other verb takes the
  INDEX form, which is a plain path step and has always worked. An unresolved
  `$send:` token becomes `SPATH_INVALID` and the verb refuses; it never
  addresses something else.
- **A `$`-token is never a ROOT QUALIFIER.** A spec splits on its first `:`, so
  `$send:Reverb` would otherwise parse as the arrangement `$send`. Text before
  the first colon that begins with `$` is part of the PATH.
  `SProject::registerArrangement` refuses a name beginning with `$`, so the
  reservation is enforced rather than assumed.
- **A mistyped sentinel fails CLOSED.** `$mastr` resolves to nothing rather
  than to track 0 — `stringToPath` used to accept any non-numeric text.

### What a system lane REFUSES, and what it accepts

Every refusal is ANNOUNCED with a `TW_LOG` line naming the verb and the lane;
none is a silent no-op, and each leaves the model untouched.

| | Verbs |
|---|---|
| **REFUSED** | every PLACEMENT (`add-sample`, `place-clip`, `place-recording`, `place-asset`, `move-clip`/`duplicate-clip` as a DESTINATION, `add-take`, `insert-midi-clip`, `place-midi-recording`, `import-midi-file`, `duplicate-asset-here`); `arm-track`, `set-monitor-mode` (every mode), `set-track-input`; `set-track-solo`; `set-track-midi-output`; `remove-track`, `move-track`, `reparent-track`; and `insert-plugin` for an INSTRUMENT |
| **ACCEPTED** | `set-track-volume` and `set-track-mute` (both HEARD — the fader and `twGainStage`'s audio mute) — except that `set-track-volume` REFUSES the conductor, which carries no audio, as `set-track-pan` does; `set-track-mute` is still accepted there because mute also drives the lane/clip colour, so it is not inert (QBX-114); `set-track-name`; `set-lane-hidden` (which REFUSES a lane that is not a system lane — the inverse rule); the four other plugin verbs, so a master or send insert chain is fully editable; and every automation verb |

`set-track-solo` is refused where `set-track-mute` is accepted, and the
asymmetry is the point: a system lane is outside `childLinks()`, which is
exactly what `ssolorules::anySoloInTree` walks — so a solo flag there is state
no audibility rule can ever read, while a mute has `twGainStage` to carry it.

**Every registered track-addressed verb carries an explicit accept/refuse row
in `action_roundtrip_test`**, and a verb added later with no row FAILS THE
SUITE. The policy is a blacklist, so it is default-OPEN; that audit is the
mitigation.

### Send ROUTING (proposal 47)

A SEND is a TAP on a source lane naming a destination send lane **by name**
(D2) — `SSendTap{ dest, levelDb, preFader, enabled }`, held on `SObject` and
serialized inline with its owner exactly as an automation lane is. Four things
about it are not guessable from the verbs:

- **A source's tap point is post-FX**, always. `pre="true"` taps BEFORE the
  fader (`twGainStage`'s input) and `pre="false"` — the default — taps AFTER
  it. **Pre-FX is not offered** (D3): an insert chain is what a send is usually
  for, and a pre-FX send would need a second tap component per track for a
  routing nobody asked for.
- **The wiring is done by `reconnectTracksToMixer`, in the same pass that wires
  every other input** (D4, and proposal 45's trap T3). Anything wired beside
  that pass is clobbered by the next audibility, solo, mute or arm change, so
  `add-send`/`remove-send`/`set-send` all commit through
  `SStdMixer::sendRoutingChanged()` and never touch a plug themselves.
- **Audibility is ASKED, never re-spelled** (D5): a source that
  `ssolo::isLaneAudible` calls inaudible feeds nothing, and a LIVE-OWNED lane
  feeds nothing either (D9 — a monitored input is rendered by the live pump,
  which has no send path at all, so a send from an armed track goes quiet for
  the duration of the arm and comes back on the hand-back).
- **A CYCLE is REFUSED at the verb and BROKEN at the wiring** — both, because a
  file can carry one the verbs never saw. `add-send` walks the tap graph and
  refuses an edge that would close a loop; `rewireSendBuses` walks it again on
  every pass and drops the edges that would revisit a lane already fed,
  announcing each with a `TW_LOGW`. D6 predicted a hang if a cycle ever
  reached the scheduler and **that prediction was wrong** — `expandNode_`
  dedups by `(component, pageStart)` and `FreezeContext::isComponentInStack`
  breaks a cycle at render — but a cycle is still refused, because "renders
  something" is not the same as "renders what the user meant".

**There is no PDC across a send** (D8) and no send from or to the MASTER lane.
